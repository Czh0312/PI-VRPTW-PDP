# 毕设改动与实施计划：单日两级配送、延后回收与一级先送后取

日期：2026-09-28。状态：单日核心实现与代表实例验收已完成；正式完整实验和经济评价待实施。使用说明见 [M3 单日基础版](model3_single_day_backhaul.md)。下文保留原实施计划及规划时的现状对照。

本文依据本次讨论和当前代码核对形成。实施先完成单日基础版，再决定是否进入多批次扩展；不把未来功能提前塞入基础版。

Material Passport：Origin Skill = academic-research-suite / experiment-agent；Origin Mode = plan；Verification Status = PARTIALLY_VERIFIED（核心实现、回归及代表实例已验收；正式全量实验、经济结论仍未验证）；Version Label = single_day_baseline_plan_v1。规划时现状判断与本次实施证据分开记录。

**1．将研究主线调整为真实装卸规则下的两级配送与延后回收协调。**

保留总仓—前置仓—顾客网络、可循环容器、顾客本单的延后回收，以及与一次性包装的经济比较。取消以顾客地点暂存空箱的车辆间中转，不新增中转站。已有中转模型和结果保留用于追溯，不作为新基础版的默认优化机制。

基础研究问题：在每天一个订单批次、一级车辆先送后取、各前置仓空箱收齐后一次性取走的条件下，如何联合安排两级路线与时间，使当天业务可行，并控制运输距离和车辆等待？

新增先送后取约束首先是业务修正，不预先宣称它会降低距离，也不把它单独称为已证实的学术创新。后续通过算法、运营策略和容器周转实验建立研究贡献。

**2．冻结已经确定的规则，并标明本计划补充的实施默认值。**

| 维度 | 已确定的业务范围 |
| --- | --- |
| 配送批次 | 一天一个整体订单批次，不等于只使用一辆大车 |
| 订单信息 | 基础版按当天需求已知的静态问题处理 |
| 一级作业 | 每辆大车完成本趟全部配送后，才能执行回收；不要求全车队同时结束配送 |
| 二级作业 | 保留配送和本单延后回收；不要求小车也采用整趟先送后取 |
| 前置仓取箱 | 每个有回收需求的仓，当天空箱全部回齐后，由一辆大车一次性取走 |
| 局部等待 | 等待的是当前被回收的仓，不是全部前置仓同时收齐 |
| 初始空箱 | 前置仓不预置空箱；允许回收箱在仓内日内暂存 |
| 中转 | 不允许二级车辆通过顾客点或额外设施转交空箱 |
| 回收范围 | 二级当天完成回收；跨批次回收留到后续 |

为使第一版可以实施，本计划补充以下默认值。它们是建议的模型边界，不冒充用户已经逐项指定的事实：

- 固定顾客分仓，以 M3 为主线；M4 自由分仓在基础版通过验收后再接入。
- 采用完整当日闭环：一级车辆在显式日终期限前把全部当天回收箱带回总仓，并完成配置要求的卸箱。二级当日回仓和一级当日闭环分别检查。
- 每辆一级车一天最多一趟，每辆二级车也沿用当前单趟结构；不引入车辆多趟调度。
- 每仓一次一级配送、一次一级回收；不拆分同仓的配送或回收量。
- 同一仓的一级配送车和回收车不强制相同；二级配送与回收任务也不新增同车绑定。
- 保留旧模型对纯配送路线、纯回收路线的许可，统一受原车队数量上限约束。先送后取适用于同时承担两类任务的路线；不暗中增加“每车必须同时送取”的约束。输出单独列出这两类路线，便于评估运营接受度。
- 当天不丢箱、不新增采购、不把回收箱再次装货发出。容器规格与回收数量按实例明确给出。
- 前置仓日内存放和装卸资源先视为充足，不优化库容和月台排队；仍输出峰值暂存箱量，说明该假设所需空间。有限库容作为后续情景。
- 发车基准时间统一记为 t0，装车准备已在 t0 前完成；基础版沿用统一时间锚点，不另加发车时刻优化。清洗在回总仓后处理，不研究当天再次利用；若按日重复运营，须说明可在次日发车前完成处理的假设。

日终期限、装卸时间和时间单位需要在具体案例配置中明确。不能把算法的 Big-M 时间上界、文件名中的 same_day，或者默认 24 小时，直接当成经过业务确认的日终参数。缺失时应给出明确配置错误；不自动放宽期限直到实例可行。

**3．用明确的任务与时间关系描述基础模型。**

每个顾客有配送任务 i^d 和延后回收任务 i^p；每个活跃前置仓有一级配送任务 s^d 和回收任务 s^p。前置仓回收量由所属顾客应回收容器数汇总得到，不作为可自由减少的变量。

一级路线满足 `总仓 → 配送任务段 → 回收任务段 → 总仓`。允许其中一段为空；两段都非空时，所有配送节点在所有回收节点之前。回收顺序可以不同于配送顺序。

核心约束如下，实施时保留现有任务覆盖、路径连通、车辆数、重量与体积容量和顾客时间窗约束：

| 约束 | 数学含义与实施要点 |
| --- | --- |
| 一级作业顺序 | 禁止任意一级回收任务直接接任意一级配送任务，即所有 p→d 弧都禁用，不限同仓；在闭合且无子环的单趟路径中保证任务类型为 d* p* |
| 前向衔接 | 二级出发时间 ≥ 对应仓一级卸货完成时间 + 必要的分拣/装车时间 |
| 顾客先送后取 | 回收开始时间 ≥ 配送服务完成时间；继续遵守输入配送/回收时间窗。若另设最短使用时长，必须作为显式场景参数，避免与已有回收窗生成规则重复计入 |
| 空箱收齐 | 该仓一级取箱开始时间 ≥ 该仓所有实际使用二级车辆的回仓卸箱完成时间；当前基础版保留“全部二级车辆返回”的现有语义 |
| 日终闭环 | 一级最后任务服务完成 + 回总仓行驶 + 必要的总仓卸箱 ≤ H；二级回仓完成也须在其运营时限内 |
| 数量守恒 | 无损耗基础版中，各顾客配送箱数 = 回收箱数；顾客、前置仓和一级回运汇总一致 |
| 初始容器供给 | 一批发出且日内不重复装箱时，固定容器池 N ≥ 当天配送箱数之和；不把固定总量误写成任意时刻总仓都有 N 个可用箱 |

设 r_v 为二级车 v 到仓时刻，u_v 为其回仓卸箱时间，则仓 s 的最早完整取箱时刻为：

`R_s = max{ r_v + u_v : v 是该仓实际使用的二级车 }`。

大车可提前到达并等待，但取箱服务不能早于 R_s。各仓单独计算 R_s，不设置全城统一收齐屏障。若同一站包含“最后一次送货”和“随后取箱”，可以连续执行，但仍须等待该仓二级回收完成。

一级和二级服务时间的含义须逐项核对：到达、开始服务、卸货完成、空箱可供装载不能混用。已有服务时间中包含的作业不能再次叠加。未观察到的装卸时间标为情景假设。

**4．先固定可比目标，再扩展时间与经济评价。**

第一版的模型验证目标沿用 `min(D_E1 + D_E2)`，以便核对两个精确后端并隔离业务规则变化。日终完成是硬约束；同时报告车辆等待、工作时长和各仓就绪时间。此版本不得声称“已经最小化等待成本”。同一路线统一输出最早可行时刻表，避免精确解中任意时间松弛污染等待统计。

基础版验收后，若论文需要评价距离与等待之间的经济权衡，再实施一个明确版本的运营成本目标：行驶相关成本 + 车辆工时成本 + 必要的启用成本。精确求解、ALNS 和审计使用同一目标。成本系数须有出处或明确作为情景参数；每公里全成本已包含的人工/折旧不得与每小时成本重复计算。

容器采购、清洗、扫描等在单批固定需求下可能是路线决策的常数，仍应进入经济评价；不必为了形式完整把不影响路线的常数都塞入求解目标。容器池初始投入和后续运营成本分别报告。

**8．精确模型和 ALNS 都要处理完整路线，不能只在最终报告中过滤违规解。**

精确模型实施细节：

- 货物流后端只对一级图禁用所有 p→d 弧；对返回总仓的已选弧加入 `t_i + service_i + travel(i,O) + depot_unload ≤ H` 的条件约束。二级返回弧继续衔接到本仓取箱时刻，并加入卸箱时间。
- indexed 后端增加相同的禁弧与回仓时间约束；使用车辆启用条件释放未使用车辆，不能将出发总仓时间变量同时当作返回时间。
- 检查时间上界、不可行弧裁剪、热启动和提取逻辑。旧解只能在通过新审计后作为新模型热启动。
- 两个后端保留原有零距离/零服务子环保护；不能指望时间推进自动排除所有零时长子环。

ALNS 实施细节：

- 初始解按配送段与回收段构造；配送任务只插入配送段，回收任务只插入回收段。
- 跨车移动、交换、整段交换、破坏修复都检查最终顺序、容量和新时间约束；不要只修改一个评估函数而保留失效缓存或旧修复器。
- 配送路线改变会影响二级出发，二级路线改变会影响前置仓就绪，进而影响一级回收和日终返回；按依赖重新计算完整时刻表。
- 缓存键与缓存生命周期必须包含策略、服务参数、日终期限和目标版本，避免跨规则复用。
- 构造失败或限时内找不到可行解记为 `no_feasible_found`，不得当作数学不可行。只有求解器证明或严格必要条件可以支持不可行判定。

**9．用针对业务错误的测试验收，而不是只检查程序能运行。**

拟新增核心测试文件 `tests/routing/test_single_day_backhaul.py`，并扩展现有精确/ALNS/审计功能测试。以下是必须覆盖的行为，而非要求每行机械地创建一个测试函数。

| 场景 | 应验证的结果 |
| --- | --- |
| A送→B送→A取→B取 | 在容量和时间可行时允许 |
| A送→A取→B送→B取 | 新策略拒绝；旧混合作业策略在满足其他约束时仍可允许 |
| 最后送货仓与首先取箱仓不同 | 允许，不人为绑定逆序 |
| 一个仓已收齐，另一仓未收齐 | 已收齐仓可以被取走，不施加全局屏障 |
| 大车早到取箱仓 | 等至该仓全部二级回仓卸箱完成后再服务 |
| 最后一站取箱按时，但回总仓超时 | 必须拒绝 |
| 未使用车辆、空路线、仅一种任务的路线 | 按启用与既定业务规则处理，不产生虚假等待或虚假日终违约 |
| 一级与二级 p→d 的区别 | 一级跨仓 p→d 拒绝；二级可先取甲再送乙，但同一顾客仍须先送后取 |
| 配送车和回收车不同 | 不误加同车绑定；任务仍恰好覆盖一次 |
| 非零装卸时间、同地点零行驶时间 | 无漏计/重复计时，无零时间子环 |
| 送出箱数与回收箱数不一致、N不足 | 新无损耗场景给出明确错误或不可行判定 |
| 两个后端与 ALNS | 在同一策略、实例和单位下接受同一可行路线；精确后端最优目标一致 |
| 序列化后重新加载 | 审计结果、总距离、回仓时间和策略版本一致 |
| 旧策略回归 | 未启用新策略时，受影响的旧模型功能不发生无意变化 |

不要求不同算法输出完全相同路线或相同等待量，因为最优路线可能不唯一。精确最优目标一致与各自路线有效是主要标准。缺少 Gurobi/许可证时，非求解器审计与 ALNS 检查仍可运行，但不能报告完成了精确后端验证。

**10．实验围绕模型正确性、算法质量和运营代价三条证据链展开。**

研究假设先作为待检验问题，不预写“必然节省”：

- H1：在其他规则和目标相同的条件下，限制一级先送后取会缩小可行域；其精确最优距离不会低于放开顺序的对应模型。它是业务约束的代价，不是算法改进收益。
- H2：联合调整配送与回收顺序，可能优于固定配送顺序、固定逆序取箱等执行策略；改进幅度取决于回收时间窗和路网。
- H3：缩短顾客使用时长或放宽日终期限可能改善可行性和等待，但费用及距离变化需要计算；不能用单一 seed 或个别实例概括全部场景。

| 实验组 | 设置 | 输出 |
| --- | --- | --- |
| A：机制小例 | 1–3 个仓、少量顾客，刻意构造早到等待、跨仓先取后送、日终越界等 | 路线、时间轴、逐项约束验算 |
| B：小规模精确 | Zhou Set1 的 22 个 7/10/12 客户基础实例，先筛查/标明时间和容量适用性 | 目标、下界、gap、证书、后端一致性、可行性 |
| C：ALNS质量 | 与 B 相同实例，参考已证明最优解；未证明时单独报告 bound gap | 可行率、最优 gap、运行时间 |
| D：规模实验 | Zhou Set2 的 18 个 100/200 客户实例 | 多 seed 距离、等待、完成时间、可行率、运行时间 |
| E：运营策略对照 | 联合优化取箱顺序、固定逆序取箱等；同输入、同限制、同预算 | 策略代价与等待分布，不混入不同可行域或预算差异 |
| F：真实道路案例 | LaDe-D 杭州已保存的 OSRM 里程/时间矩阵 | 路线可行性、实际公里、日内周转和包装成本比较 |

运行安排：先用一个机制例和一个原始小例做 smoke；通过后小规模精确每例默认 300 秒，两个后端交叉验证先覆盖代表小例和全部机制例。正式 ALNS 采用相同墙钟预算，基础预算 10 秒，seed 42–46；需要评估收敛时再增加统一的 60 秒组，不对个别失败实例偷偷加时。预算、seed 集合和调参实例在正式比较前冻结。

所有求解进程设置单次预算及外层超时，保存每例结果和失败原因；先估算完整批次总运行量再执行。实例失败不静默重试或删掉；修复代码后重跑受影响的完整对照组并保留旧运行记录。正式研究不以“所有实例都可行”作为人为调参目标。

新增 runner 拟为 `experiments/runs/run_single_day_backhaul.py`，汇总拟为 `experiments/analysis/summarize_single_day_backhaul.py`。这两个路径目前是计划项；实现后先用其 `--help` 核对准确命令和参数，不把尚不存在的命令标为已可运行。

参数敏感性先做单因素或小型设计，避免一次全因子爆炸：顾客回收时间窗/使用时长、日终期限、E1/E2 车数、重量与体积容量、装卸时长。改动需求或容量时重新检查每仓集中配送/回收是否能由一辆一级车承载。

**11．所有结果同时报告路线与时间，不把限时解写成最优。**

最低输出字段：

- 总距离及 E1/E2 分项、启用车辆数和纯送/纯取路线数。
- 大车各站到达、服务开始、服务完成、离开和最终回总仓完成时间。
- 二级各路线出发、顾客配送/回收与回仓卸箱完成时间。
- 各仓全部空箱就绪时间、取箱时间、等待量、峰值日内暂存箱数。
- 当天送出、顾客回收、入仓、一级带回箱数及差额。
- `status`、`proven_optimal`、`objective_mode`、`objective`、`best_bound`、`mip_gap`、构建/热启动/求解时间、`route_audit.valid`。

独立审计检查实际提取路线，不直接信任求解器变量。主距离目标下统一重建最早可行时刻表；不把不同算法任意选择的服务时间松弛当作等待差异。待进入时间成本目标后，输出与审计必须核对实际目标调度，不能擅自重新排程改变所声明的成本。

只对已证明最优的参考值计算“相对最优 gap”。未证明最优时报告 incumbent 与有效下界；ALNS 无解、精确限时无解、已证明不可行分别列出。多 seed 报告均值、标准差及可行率，失败不能当作零距离，也不能通过只保留成功子集造成选择偏差。

新旧规则若同时改变 H 和作业顺序，应拆分实验：先在相同 H 下比较混合与先送后取，再单独分析 H。历史无日终限制的数值只能作历史记录，不能直接用来量化单一约束的影响。

**12．经济评价与论文同步修改，避免沿用旧周转假设。**

基础比较为相同分仓和相同服务需求下的纯配送 M1 与新单日 M3。一次性方案保留合理的装载物理假设，不强行施加空箱回收。接入自由分仓后再做 M2 与新 M4，并保证每客户箱数、单位和日终规则一致。

新单日经济配置重新核算初始容器池。若一天只装一次，N 的基础下界来自当天总用箱量；重复运营还需说明夜间清洗和次日可用性。不能直接沿用当前 LaDe 配置中按约 2.35 天回收周期和清洗缓冲构造的 900 箱来解释单日结果。

路由基础版采用无丢失闭环；现有成本配置的非零损耗率只能作为另行标明的长期损耗/补充采购敏感性，不能同时声称跨多日系统“无采购且数量永远不变”。初始投资、补充采购与摊销分清，不重复收费。

现有按每单里程线性放大的成本接口，只能作为费用情景近似。若研究需求规模变化对路线、车辆或容器池的影响，须重新生成相应需求并重新求解，不能把比例缩放当作新的优化结果。

Zhou 坐标用于算法比较，不直接视为真实公里或人民币预算。LaDe 的真实路网距离与配送信息，与人工构造的包装回收窗、装卸参数和容器假设分开标注。现有 same_day 文件名不保证在新的 H 下可行；使用 next_day 场景属于未来研究，不混入基础版主表。

论文更新内容包括：问题背景和运营流程图、假设表、任务与同步约束、一级先送后取公式、求解方法、实验设计、时间轴及路线图、成本分解、局限与扩展。中转部分转为研究过程/未采用方案说明，不继续作为主贡献；不删除历史程序与结果。

**13．用明确验收标准决定基础版是否完成。**

- 新案例端到端运行时确实调用新策略；默认精确后端、indexed 后端、ALNS 和审计的语义一致。
- 全部核心机制测试通过；新约束造成的不可行有明确解释，未通过放松规则或隐藏失败掩盖。
- 每个交付解都满足任务覆盖、容量、顾客先送后取、一级整趟先送后取、各仓收齐再取和日终回仓。
- 时间和箱量输出能独立复核；新目标/新规则标识与序列化结果一致。
- 完成机制例、小规模精确、18 个大规模实例的预定多 seed 运行，以及至少一个真实道路案例的分析；“完成”包括如实报告未解出或不可行，不保证全部成功。
- 旧模型相关回归通过；新实验未覆盖旧结果；报告不会把时间限制解当成最优。
- 单日容器池与经济参数重新核对，论文结论只使用对应新版本的结果。

最终交付拟包含：新运营配置与案例、模型及算法改动、独立审计与核心测试、实验 runner、原始 JSON/CSV、分析报告、可导出的路线/时间轴图，以及更新后的问题定义和论文图表。建议新结果根目录为 `output/experiments/single_day_backhaul/<run_id>/`。

**14．基础版通过后，再沿下列顺序增加复杂度。**

| 扩展 | 新增决策/约束 | 与基础版的关键差别 |
| --- | --- | --- |
| F1：固定多批次 | 给定截单与发运间隔、订单归属批次、车辆多趟时间衔接 | 首先只研究多波次运作，仍可要求各批空箱随本批回程收齐；批次能否重叠需明确定义 |
| F2：跨批次取箱 | 每次取箱地点和数量、真实入库事件、后续取走事件、最大滞留时间/容量 | 不再要求一次取完某批全部空箱；库存必须在每个事件非负 |
| F3：固定容器池周转 | 总仓清洁箱、在途/顾客/前置仓/待清洗箱守恒，下一批领箱可行性 | 把容器总量恒定与总仓可用量分开；F2 的正式运营评价应同时具备这层基本约束 |
| F4：可选高级扩展 | 容器池规模或批次间隔优化、随机回收时间、滚动优化、有限月台 | 视毕设进度选择，不作为第一版交付条件 |

跨批次模型保持一级先送后取；它放宽的是回收批次绑定，不是装卸顺序。有限期实验必须设置合理末端库存/尾部回收或周期状态条件，防止最后一天不回收而虚假省钱。基础版则始终保留每仓收齐一次取回的清晰边界。

当前执行入口应是 P0 的场景与参数检查，随后 P1 的规则审计；不是直接调整 M8 中转算子，也不是立即给所有变量增加批次下标。
