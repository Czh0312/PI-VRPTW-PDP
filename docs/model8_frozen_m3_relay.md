## 1. 为什么单独定义 M8

M5/M6 精确求解允许路线与交接联合决定；M8 表示另一种运营流程：普通配送回收计划
先确定，再寻找可以执行的接力机会。两个研究问题都合理，不能把联合优化本身视为错误。

现有 M6 ALNS 已有“无交接搜索 + 交接后处理”的算法流程，但其精确模型是联合优化。
此外现有 ALNS 使用任务级位置替换，M6 精确模型使用同质空箱事件数量流，机制边界需要
另行对齐。M8 不把旧算法简单改名，而是把固定基础解写入可行域，精确与 ALNS 共用
同一物理接力模型和路线承诺约束。

若第二阶段把每条实际行驶弧也完全固定，按当前距离目标，交接不改变目标值。
因此本版本冻结“原任务的车辆归属及相对顺序”，仅允许接力引起的物理路径变化。
这不是回头重做普通路径优化。

## 2. 两阶段定义

第一阶段独立求解 M3：

\[
\bar r\in\arg\min_{r\in\mathcal F_3} L(r),\qquad Z_3^*=L(\bar r).
\]

保存实际返回的一个最优解 \(\bar r\)。存在多个并列最优解时，不用第二阶段收益来
重新选择基础解；路线指纹记录本次到底采用哪一个解。

第二阶段：

\[
Z_8^*(\bar r)=\min_{u\in\mathcal U(\bar r)} L(r(\bar r,u)),\qquad
\Delta(\bar r)=L(\bar r)-Z_8^*(\bar r).
\]

\(u\) 包括是否接力、交接点、携带车及两个插入位置；\(\mathcal U\) 是下节定义的
完整合法接力集合。这里不是随机规划，也不枚举全部 M3 并列最优解。

## 3. 冻结什么、允许改变什么

| 决策 | 第二阶段处理 |
| --- | --- |
| 顾客—前置仓分配 | 固定，沿用 M3 |
| E1 车辆及完整任务路线 | 固定所有行驶弧 |
| E2 已使用的车辆集合 | 固定，不启用未使用车辆 |
| 配送任务的车辆和服务位置 | 固定 |
| 原车辆上全部原始任务的相对顺序 | 固定，包括回收任务的任务位置 |
| 无接力的回收任务 | 原车在原顾客位置实际取箱 |
| 有接力的回收任务 | 原回收车在原任务位置改为到交接点接箱 |
| 携带车 | 另一辆同仓、第一阶段已使用的 E2 车辆 |
| 新增操作 | 携带车插入原顾客取箱 TP、交接点卸箱 TD |
| 时间安排 | 可重新安排等待和服务时刻；原时间窗、先送后取和 E1/E2 衔接不变 |

本版本允许异步暂存，接收不得早于卸下完成；未增加暂存容量、最长存放时长或单独
交接费用。它们属于后续业务扩展，不能把当前里程节省直接解释为总经济收益。

## 4. 任务级接力及其物理含义

对回收任务 \(p\)，原位置为 \(o_p\)，原回收车辆为 \(b(p)\)，候选集合为同仓全部
顾客位置 \(H_p\)，包括 \(o_p\)。定义 \(y_{ph}\in\{0,1\}\)：

\[
\sum_{h\in H_p}y_{ph}=1.
\]

- \(h=o_p\)：\(b(p)\) 在原位置直接回收。
- \(h\ne o_p\)：携带车 \(a\ne b(p)\) 执行 TP、TD，\(b(p)\) 执行 RP。

链条是 `原顾客 → 携带车 → 交接点 → 原回收车 → 所属前置仓`。
原顾客回收时间窗约束 TP，RP 不重复套用该回收时间窗。TP 须在原顾客配送完成后，
TP 与 TD 由同一车完成，RP 须在 TD 卸下完成之后。

此处有意采用 M5 的任务级链条，而非 M6 的匿名 O/R 流：这样才能把“原回收任务位置”
与第一阶段承诺逐项对应。一个任务若包含多个箱子，整批接力，不按箱数拆分。
每个任务至多选择一条链，因此每箱最多发生一次车辆间转运；不额外限制每车只能参与一次。

例如，基础解中 B 的路线为 `仓 → X配送 → 甲回收 → Y配送 → 仓`。
选择在乙交接后，B 为 `仓 → X配送 → 乙接箱 → Y配送 → 仓`；A 在自己的原任务序列
之间插入 `甲取箱 → 乙卸箱`。A/B 原有任务顺序都不改变。

## 5. 固定路线承诺的数学表达

复用 M5 的 \(x,z,y,A,Q,V\) 变量及全部物理约束，再加入：

1. **E1 固定**：\(x_{ijk}=\bar x_{ijk}\)。
2. **任务所属车固定**：配送节点和每个回收候选 RP/直接回收节点只能由其原车访问。
3. **禁用新车**：基础解未使用车辆的全部 E2 弧变量为 0。
4. **原任务顺序固定**：给每个操作节点设拓扑位置 \(\rho_{iv}\)，每个原任务设任务位置 \(s_t\)。

对非仓节点之间的弧：

\[
\rho_{jv}\ge\rho_{iv}+1-M(1-z_{ijv}).
\]

对配送任务，\(s_t=\rho_{t,b(t)}\)；对回收任务，用指标约束：

\[
y_{ph}=1\Rightarrow s_p=\rho_{RP(p,h),b(p)}.
\]

对基础路线上的每对相邻原任务 \((t,t')\)：

\[
s_{t'}\ge s_t+1.
\]

TP/TD 不属于原任务位置，可以插入空隙；其数量、承运人一致性、先后和载荷变化由
M5 物理约束决定。正的拓扑增量同时排除零距离、零服务时长下的断开子回路。

必须禁用 M5 通用车辆编号对称约束：在 M8 中编号对应固定承诺，不能再随意交换。
这不改变物理约束，只移除不适用于固定车辆身份的对称剪枝。

## 6. 精确求解与证明范围

1. 求 M3，要求零 gap 的最优证明；预算默认占总预算 60%。
2. M3 未证明最优则跳过第二阶段，返回 `BASE_OPTIMUM_NOT_PROVEN`。
3. 验证基础解的任务覆盖、车辆数量、容量、时间窗、先送后取及两级衔接，保存路线指纹。
4. 构造上述完整第二阶段 MIP，保留全部同仓交接点、已有车辆及合法插入位置。
5. Gurobi 在零 gap 下证明最优后，报告给定基础解的条件最优。

| 字段 | 含义 |
| --- | --- |
| `stage1_proven_optimal` | 此基础解的 M3 最优性是否得到证明 |
| `conditional_proven_optimal` | 给定该基础解，完整第二阶段是否证明最优 |
| `two_stage_proven_optimal` | 前述两项都为真；不表示遍历过所有并列基础解 |
| `proven_optimal` | 始终 False，避免被普通总表误计为联合路径全局最优 |
| `conditional_best_bound / conditional_mip_gap` | 完整第二阶段的下界和 gap |
| `baseline` | 原始路线、原目标值、路线指纹 |

ALNS 中固定部分传递模式得到的局部修复下界不作为完整第二阶段下界。
给外部 `base_routes/base_info` 时，必须传入同一次、同一实例的 M3 结果；程序复核可行性
和目标值，但不会仅凭调用者传入的布尔标记重新建立 M3 的最优证明。

因为允许零交接，完整第二阶段含原基础路线。与 M5 使用相同业务参数、时间约束和
距离目标时，有：

\[
Z_5^*\le Z_8^*(\bar r)\le Z_3^*.
\]

右式用于解释最优值；实现也始终保留无交接基础解，限时输出不会劣于基础解。
M6 的事件范围与任务聚合方式不同，不直接声称与 M8 存在同样的包含关系。

## 7. ALNS：只搜索传递，不重新搜索基础路线

默认同样先取得 M3 已证明最优解；建议精确版与 ALNS 直接共享一份基础解。
状态是各回收任务的“直接/交接点”模式，以及当前可行路线。基础解是初始可行解。

破坏算子：随机释放若干回收模式、释放同一原回收车的模式、优先释放已有接力模式。
修复算子：短预算 MIP 与深预算 MIP。未释放任务的直接/交接位置不变；释放任务可在
全部同仓交接点中重新选择，修复器同时重排合法的 TP/TD 插入操作和时间安排。
既有接力的携带车及插入位置允许在修复中共同调整，但任何原任务顺序都不改变。

使用模拟退火接受、全局最好解保留、按全局改进/当前改进/接受分级奖励，并周期更新
破坏与修复权重。没有改变 \(\bar r\) 的外层搜索或把剩余时间退还给 M3 的步骤。

这是 **ALNS + MIP 修复的混合算法，需要 Gurobi**。它不是现有无需商业求解器的纯
ALNS 版本。默认每次最多释放 3 个回收任务，不声称完整枚举；只有某次无模式限制的
修复证明了完整第二阶段最优，才允许返回条件最优标记。

显式指定 `stage1_method="alns"` 可研究“大规模 M3 最好已知解上的传递”，但此时基础解
未证明最优，属于另一个实验口径，不得与默认最优基础解实验混为一谈。

当前实现面向小规模机制验证。完整任务×交接点展开增长较快；大规模运行还需候选生成、
路线插入专用修复与增量调度优化。时间预算涵盖建模，但一次模型构建不能中途抢占，
极大实例可能在建模阶段超过墙钟预算；到达截止时间后不会再启动优化器。

## 8. 运行和比较

需要 Python 3.10+、Gurobi 与有效许可证；测试还需 pytest。

本次实际验证使用临时 Python 3.12 环境 `/private/tmp/m8-validation-venv/bin/python`，
安装了 Gurobi 12.0.3、pytest 及命令行绘图依赖。项目原 `.venv` 是 Python 3.9，
没有替换它；运行前应选择满足版本要求的环境。

```bash
python main.py route --model 8 --solver exact --exact-time 60
python main.py route --model 8 --solver alns --time 60

# 推荐：先求一次 M3，两种第二阶段算法共享完全相同的基础解
python -m experiments.runs.run_model8_two_stage --base-time 30 --stage2-time 20
python -m pytest tests/routing/test_model8.py -q
```

分别运行两个 CLI 命令可能得到不同的 M3 并列最优解，不能据此直接归因算法差距。
比较脚本会验证基础路线指纹一致；原始结果保存到 `output/experiments/model8_two_stage/`。

截至本次实现，回归验证覆盖：无接力严格退化、强制物理接力、承运与接收车辆、时序、
固定任务车辆与顺序、基础解篡改/证书不匹配、未证明基础解时跳过第二阶段，以及两算法
共享基础快照。没有宣称完成独立于求解器的全部数值调度审计。

首个 Zhou 7 客户例中：M3=337.617968，M8 精确=337.617968 且条件最优已证明，M8 ALNS
也为337.617968。该基础解没有正里程收益传递；这不代表其他实例或其他并列最优基础解
均无收益。详见本次实际[验证报告](../output/experiments/model8_two_stage/report.md)。

## 9. 对原机制的判断

需要澄清的不是“传递一定要两阶段”，而是业务是否允许为传递重新设计普通路线。
联合模型适合一体化规划，M8 适合计划已形成后的机会识别，两者应作为不同策略比较。

当前传递的运营假设仍包括同仓、单次、可异步暂存、任务整批移动。这些不是数学必然，
应在论文中明确。最优 M3 基础解可能已经没有可利用的绕路，且交接又增加操作，所以
不能预设 M8 一定有正收益。发现并严格证明零收益也是有效机制结论。

## 10. 大规模试跑（2026-09-21）

在标准当日回收场景、种子42下试跑100/200客户代表实例。M3 ALNS预算20秒，M3精确
证明预算20秒，传递搜索预算30秒。100客户的M3证明最优（1449.239074），第二阶段
完成6次可行修复但未改进；严格松弛下界1441.058624，可能节省的上界约0.565%，
没有证明零收益。200客户的M3上界2157.073012、下界2089.283152，gap约3.143%，
因此只作最好已知基础解上的探索性测试。

200客户首轮30秒几乎全部用于建模，没有完成有效修复。对相同基础解延长一次修复预算
后，完成1次修复但仍未改进：建模约30.21秒、总耗时33.35秒，412620个变量、2373891条
约束，峰值RSS约1.88GiB。当前瓶颈是每次局部修复仍然构建整个实例的MIP。

这两例不能支持“传递无效”或普遍性能结论。大规模完整M8展开式MIP尚未构建求解，
额外只计算了严格松弛下界。下一步优化方向是只对受影响路线构建修复子问题，并保留
其他路线对时序、容量和接力的边界条件，避免反复重建整个网络。
实际参数、原始结果和补测链接见[大规模报告](../output/experiments/model8_large_probe_20260921/report.md)。
