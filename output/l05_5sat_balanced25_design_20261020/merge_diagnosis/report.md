# 一级多仓合并不足：固定输入局部诊断

结论：当前“一车一仓”不是需求时间窗强制形成。固定原M8冷启动解的订单分批、批次起止、回收分界及箱池36，仅重新组织一级配送与回收路线，就得到7趟而非14趟的可行方案，且成本更低。
该反例直接说明原ALNS结果遗漏了可行的合并空间；不能据此将责任归于需求时间设计。日历/回收时序仍会影响进一步合并，但需要与外生订单窗口区分。

## 固定全部时间决策的主对照

| 指标 | 原M8冷启动ALNS | 联合合并局部诊断 |
|---|---:|---:|
| 一级趟次 | 14 | 7 |
| 一级出仓体积装载率 | 28.57% | 57.14% |
| 箱池 | 36 | 36 |
| 总成本 | 464.9261 | 406.5566 |
| 一级距离 | 1730.4129 | 1146.7178 |
| 二级距离 | 2197.6955 | 2197.6955 |
| 两周期重放 | 通过 | 通过 |

第一批的一个可行合并路线依次向S3、S5、S6配送，共21箱，容量25箱，出仓体积装载率84%。另一辆车服务S9、S2，共15箱。原有订单需求与时间窗均未改。
输入哈希、算法源码、订单分批、箱池、批次边界和回收分界均核对不变；E2任务顺序、等待下界与行驶距离保留。一级供货改变后，解码器按原约束重新传播实际服务时刻。

## 代码层面的机制

1. construction.py 的 initial_state 按新路线总距离比较车辆选择，没有扣除该车辆原路线距离。在欧氏距离下，只要还有空车，这通常会使空车的独立往返看起来更便宜，造成单仓单车的初始构造偏向。
2. neighborhoods.py 的 e1_delivery 每次只随机移动一个仓点；e1_pickup 独立随机改变回收顺序及车辆提示。没有一个显式操作同步合并整条配送路线、重排回收并释放原车。evaluator.py 的回收解码还优先维持车辆提示，距离排在提示之后。
3. 60秒总预算分配给1…100个K。当前两个原解实际用于K=3的运行时间约21秒，迭代分别为334和321。有限搜索从偏单仓的初解出发，未充分消除这种结构。
这些机制与可行合并反例共同支持“构造和搜索不足”的诊断；并未证明某个因素独自解释所有差距。

## 回收分界的补充检查

对原可行初解启动ALNS的箱池35方案，固定所有时刻决策时联合合并已能将15趟降至11趟、成本453.6484降至422.7898。
再仅调整M8本就允许优化的回收分界，各批提前10分钟或20分钟，得到更紧凑的可行路线。订单时间窗、清洗时间、使用时间和批次边界仍不变。

提前分界并非任何情况下都可行：原冷启动方案直接提前10/20分钟、其他原始路线不动时触发TERMINAL_OUTSTANDING。补充检查保留这些失败，不将其解释成整个日历域不可行。
因此需要协调配送、回收与分界，而不能简单要求所有分界统一提前。

## 方法与范围

局部诊断枚举同批两条一级配送路线的合并、车辆保留选择、配送顺序及回收顺序；每轮接受成本最好的可行改进，最多8轮，不修改ALNS源码。诊断是额外局部改进，具有额外计算预算，不是原60秒ALNS输出，也没有全局最优保证。
全部报告为可行的诊断候选，已按原M8模型独立审计、逐单窗口、两级容量、车辆占用、库存清洗与连续两周期重放。
E2任务顺序和等待下界固定；服务时刻仍由解码传播，不能称所有车辆时间表逐字不变。
可复查文件：summary.json列出所有候选统计，integrity.json保存输入哈希，完整方案按场景名称保存为JSON。诊断脚本为diagnose.py。

建议优先改进初解的增量费用评分，并增加一级配送/回收/分界的联合合并与局部精修；之后按同一预算、多种子复跑。现有证据不支持先通过重写需求窗口强行制造合并效果。
