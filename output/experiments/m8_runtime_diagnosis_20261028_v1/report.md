这里 INFEASIBLE 的准确含义是在给定批次、回收批次、车次任务划分及初始成本上限 U 下无解，不等于宣称该组合在所有成本下都业务不可行。

同一候选方法对 S05 的三个控制种子都只需检查 12 个组合，算法循环分别为 15.82、4.31、2.81 秒。因而快慢差距不能只用订单数或初始 gap 解释。S03 需要排除更多组合；S08 的单个组合本身更难检验，还需要返回同一组合继续求解。

S03 的主要瓶颈是主问题搜索，其完整子问题合计只用约 1.16 分钟。S08 的主要瓶颈是完整子问题，合计约 26.61 分钟，其中 TIME_LIMIT 调用用时 732.34 秒，确证 INFEASIBLE 用时 864.54 秒。

## 当前算法表达的具体限制

主问题使用乐观路线成本与放松的同步条件；实际车辆排程、路线访问顺序、截流全取、清洗库存和整数时钟要在完整子问题中检验。因此主问题仍会提出很多无法在原约束下达到当前最好成本的组合。

当前排除约束以整个 `K + 配送分批 + 回收分批 + 车次任务划分` 为条件。它能安全否决该完整组合，但没有提取造成失败的更小冲突集合，以便同时否决一批相似组合。条件成本割也基本作用于同一个完整组合。该剪枝方式正确，但复用失败原因的能力有限。

代码已经缓存同一完整组合的模型；但每遇到一个新组合，仍会调用原完整模型构造器并添加任务划分约束。643、312 个不同组合因此伴随大量模型构造工作。其确切时间占比仍需进一步 profiling，现有记录只给出上述未细分余量。

## 与其他模型或方法比较时

如果比较对象是 M6/M7 等固定或均匀批次模型，M8 的自由批次边界还要与订单分批、两级路线、回收清洗和箱池库存联动。相同订单数不代表相同搜索问题；这也不意味着 M8 在每个实例上必然更慢。

如果比较对象是 ALNS 等启发式方法，其运行结果通常不包含排除所有更优方案的全局证明。找到好方案的时间与证明其最优的时间应分别统计。本轮两例成本没有改善，但完成了最优性证明。

本轮未单独测量 CPU 负载、线程数、对称性处理或不同业务约束各自的因果贡献，不能将上述时间差进一步归因于某一条具体约束或硬件因素。

## 优先验证的改进方向

1. 在主问题加入有效的时间、回收和库存必要条件，减少需要交给完整子问题检验的无效低成本组合。
2. 从已确证的冲突中提取更小的决定集合，构造能同时排除多个完整组合的有效约束，保持原问题全域最优证明范围。
3. 按 K 和派生槽位上限复用模型模板，减少每个新组合重复调用 Python 构造器的工作。
4. 在上述改进后再做相同输入、相同证明标准的对照，并分别报告寻找可行解和证明最优的耗时。

这些是根据现有计时与代码定位的优先验证方向，尚未通过新实验确认收益。Gurobi 的[官方模型加强指南](https://support.gurobi.com/hc/en-us/articles/13793044538001-General-guidelines-to-strengthen-a-MIP-formulation)也建议有针对性地加强模型与有效割，并指出模型表达的改变常比单纯调整参数更有影响。
